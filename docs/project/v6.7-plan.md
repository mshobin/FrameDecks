# FRAMEDECKS 6.7 — audit and implementation plan

The plan for 6.7: universal inline editing, advanced branding, removing answers and notes, a teleprompter,
multi-select, a command palette, polish, performance and branded release notes.

**Who this is for:** the maintainer and contributors.

---

## 1. Architecture audit (what we build on)

FRAMEDECKS is **not** an Electron / React application, and 6.7 keeps it that way.

| Layer | Technology | Why it stays |
| --- | --- | --- |
| Desktop shell | Python + pywebview (the WebView2 that ships with Windows) | No bundled Chromium (Electron adds ~150 MB disk and ~100 MB RAM per window) |
| UI | Vanilla JavaScript modules (IIFEs), no framework, no build step | Instant start, no virtual-DOM overhead; each module renders only what changed (signature checks) |
| State | One JSON state (`app/js/store.js`), revision counter, conflict check | Every screen and the camera read the same state |
| Camera / outputs | Python + OpenCV compositor (`vcam/`) | One final picture for the camera, the Presentation window and previews |

React-style guidance in the request maps onto existing patterns:

| Requested technique | FRAMEDECKS equivalent |
| --- | --- |
| React.memo / efficient re-renders | Render signatures (`sig` / `inspSig` / `sigs[kind]`): a panel redraws only when its data changed |
| Shared state optimization | One store with subscribe; iframes share the parent store instead of polling |
| Debounced input | `later()` / `editItemSoon()` (350–400 ms) |
| Lazy loading | 6.7: the Excel library (930 KB) loads on first use instead of at start-up |
| Conditional rendering | Panels are built only when shown (`offsetParent` checks), the teleprompter only when open |
| Virtualized lists | Not needed at church scale (≤ 200 Frames, ≤ 1,000 items per list); revisit if measurements say so |

## 2. Component reuse

| New capability | Reuses |
| --- | --- |
| `EditableField` (`app/js/editable.js`) | One in-place editor for Frame names, Content names, list labels and text, canvas cards |
| Canvas editing of every Content type | `preview-edit.js` (6.6): extended from Question / Scripture to every card and text Content, body and label |
| Teleprompter | The Speaker View page and its live-state logic (`speaker.js`), the Frame's existing `notes` field as the script, the window machinery of the Speaker View |
| Branding options | The Branding Content (`kind: 'brand'`) and its two renderers (`overlay.js` for pages, `vcam/program.py` for the camera) |
| Command palette | The header search (`nav.js`): same results, plus commands, fuzzy ranking and recents |
| Multi-select | The Frame and Content lists in `workspace.js`, and `SC.freshIds` for safe copies |

## 4. Decisions

1. **Answers and notes.** Removed from every screen. Stored data is kept (never deleted), so older meetings
   still open and nothing is lost; the Meeting Workbook still reads the old columns but no longer shows them.
2. **Teleprompter script = the Frame's notes.** The Frame's existing "Leader notes" field becomes its
   teleprompter script. It was already never on screen and already imported from Excel, so existing notes
   appear in the teleprompter with no migration.
3. **Audience safety.** The script lives only in the Frame's `notes`. No output path (camera, overlay pages,
   Presentation window, phone drawing pad) reads that field; a test checks it.
4. **No new dependencies.** Background removal is a canvas flood fill in the browser; the teleprompter, palette
   and editor are plain JavaScript.
5. **Discussion topics, icebreakers and polls** are Content Library presets of the existing text Content (they
   edit, brand and present like any text card). A poll is display-only: FRAMEDECKS has no audience devices
   to vote with.
6. **Backward compatibility.** New fields have defaults in `cleanLayer` / `cleanScene`; older data loads unchanged.

## 5. Performance baseline (6.6, measured in Chromium, demo data, median of 3)

| Page | Load | JS heap | DOM nodes | Scripts |
| --- | ---: | ---: | ---: | ---: |
| Main window (`dashboard.html`) | 351 ms | 10.8 MB | 2,134 | 1,590 KB |
| Phone remote (`remote.html`) | 47 ms | 2.6 MB | 320 | 112 KB |
| Speaker View (`speaker.html`) | 52 ms | 1.1 MB | 75 | 77 KB |

Server process (with the camera engine running on the test camera): about 120–126 MB resident.
Targets for 6.7: no page slower or heavier than 6.6; the main window lighter after lazy-loading Excel.
Results are recorded in [performance.md](performance.md).
